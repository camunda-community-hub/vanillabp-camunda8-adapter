# Proposal: decision 30 counts levels by their variable, not by their element id

Not a new decision. This is text for decision 30 ("A called process is told which iterations it
runs in, and the caller's model is where that is read"), which still says "element id" in three of
its four rules for a called process. The code keys those rules by the index variable since this
change. The main session decides whether the text below replaces the three paragraphs in place,
because the decision log is binding and the statement only gets more exact; nothing in it turns
around.

Replace the paragraph "Where the same element id turns up twice along ONE path, ..." with:

> Where two levels along ONE path write the same variable, the inner occurrence wins. Both write the
> same variable names and the inner scope overwrites the outer one, so the job carries the inner
> values and the chain says so. A process calling itself is where this happens by design. Two
> different element ids can be such a pair, where they differ only in characters a variable name
> cannot hold, and a DEBUG line names both.

Replace the paragraph "Where two call sites carry multi-instance elements of one id which do not
mean the same thing, ..." with:

> Where two call sites carry multi-instance elements which write the same variable and do not mean
> the same thing, the boot ends with a message naming both processes. Two different ids are such a
> case as well: `my-task` in one caller and `my.task` in another both write
> `vanillabpMiIndex_my_task`, and a job of an instance reached from one of them would answer a
> handler asking for the other with a round which never ran. This is decision 5's rule for two
> elements of one process, applied across the processes calling this one.

And in the paragraph about the reading side, "A level whose element id the called process uses
itself is dropped" becomes "A level whose variable the called process writes itself is dropped".

The reading side always keyed by the variable. The deployment side keyed by the element id, so the
two disagreed for exactly these ids. `Camunda8MultiInstanceTest` holds the refusal across two
callers, the inner level winning along one path, and the own level hiding the inherited one.
