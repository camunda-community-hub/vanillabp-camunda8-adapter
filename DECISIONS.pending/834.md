# Proposal: decision 54 reads the element template as a marker only where it stands on a job

Not a new decision. This is a paragraph for decision 54 ("Every element of a claimed process has to
be served, and an element template is how the model says it is served elsewhere"). The maintainer
answered on 2026-10-06: an element template is a marker only for jobs, and a user task is not a job.
The main session confirms the reading below with him before this goes in.

Add after the paragraph "Using the element template for this costs one miss, ...":

> The element template marks an element as served elsewhere only where the element itself is a job:
> a service task, a send task, a business rule task served by a worker, or a script task. On a
> Camunda-managed user task the Camunda Modeler uses a template to preset a form or an assignee,
> which says nothing about who serves a job, so a template there is not read as that marker. A user
> task needs no marker of its own anyway: a `@WorkflowTask` method for it is optional, and a user
> task nothing serves is named once per claimed process at INFO, the same on all three adapters.
> A naming rule for job types and a configuration key listing the job types answered elsewhere were
> weighed and not taken: the first forces a worker we do not own to take a name we chose, and the
> second stands next to the model instead of in it and goes out of date without anybody noticing.

Open for the main session: whether a listener modelled on a user task, answered by somebody else,
needs a way to say so once the template there no longer counts. Default: no, until a user asks;
such a listener is refused with a message which names it, which is the strict reading of decision 54.
