# Proposal: decision 54 says why the element template stays the marker for a listener somebody else answers

Not a new decision. This is a paragraph for decision 54 ("Every element of a claimed process has to
be served, and an element template is how the model says it is served elsewhere"). The maintainer
has not answered the question yet, so this is the default of that question: nothing changes in the
code, and the decision says why. The main session decides whether the paragraph goes in as it is.

Add after the paragraph "Using the element template for this costs one miss, ...":

> Three markers were weighed for a listener somebody else answers, and the element template stays.
> A naming rule for the job type, like the `io.vanillabp.` prefix of the listeners VanillaBP writes,
> costs the model nothing, but it would force a worker we do not own to take a name we chose. A
> configuration key listing the job types answered elsewhere would read like `allow-connectors` and
> `allow-listeners`, but it stands next to the model instead of in it, and a list of names in a YAML
> file goes out of date without anybody noticing. The element template is already read by this
> adapter, and any Camunda 8 modeller understands it. What it costs is the miss named above: on a
> user task the Camunda Modeler uses a template to preset a form or an assignee, which says nothing
> about who serves the task. A developer who sets one there for that reason, models a listener
> VanillaBP should serve and forgets the method reads a WARN instead of a refusal. That is a missed
> message and never a wrong one, and the WARN names the listener and the element.

Nothing else moves while this stays the answer: `UPGRADE.md`, the wiki pages `Configuration` and
`Deviations` and the two test models in `spring-boot/src/test/resources/listeners` already describe
and use the element template. A marker of its own would have to change all of them.
